1.1 Motivation & Problem Setup

Same setup as the Fenwick tree: an array of N integers with two types of queries repeated many times:

  • Point Update: set arr[i] = val (or add to it).
  • Range Query: compute f(arr[l], arr[l+1], …, arr[r]) where f can be sum, min, max, gcd, xor and so on.

A Fenwick tree handles sums really well because a range sum is just query(r) − query(l − 1), but that trick needs the operation to be invertible. There is no way to "subtract" a min, so range minimum with updates doesn't fit a BIT. A Segment Tree solves this. It works for any associative operation, answers both queries in O(log N), and takes O(N) space (an array of size 4N). The cost is more code and more memory than a BIT.

1.2 The Structure

A segment tree is a binary tree where every node is responsible for a range of the array and stores the answer for that range. The root covers [0, n − 1], and a node covering [l, r] splits at mid = (l + r) / 2 into a left child covering [l, mid] and a right child covering [mid + 1, r]. The leaves are single elements.

We store it in a plain array like a heap: the root is node 1, and the children of node k are 2k and 2k + 1. Using the same array as before with sum as the operation:

idx        0  1  2  3  4  5  6  7
arr[idx]   3  1  4  1  5  9  2  6

Why size 4N? The tree has height ⌈log₂ N⌉ and when N isn't a power of two the last level is partly empty, so the highest node index can go up to just under 4N. Allocating 4N is the safe standard.

1.3 Build

Build is a simple recursion: build both children, then combine them. Every node is visited once, so it is O(N).

void build(int node, int l, int r) {
    if (l == r) {
        tree[node] = arr[l];
        return;
    }
    int mid = (l + r) / 2;
    build(2*node, l, mid);
    build(2*node+1, mid+1, r);
    tree[node] = tree[2*node] + tree[2*node+1];
}
// build(1, 0, n-1);

1.4 Point Update

To change arr[i] we walk from the root down to the leaf for i, always going into the child whose range contains i, then fix every node on the way back up. Only the nodes on that one root to leaf path change, so it is O(log N).

void update(int node, int l, int r, int i, int val) {
    if (l == r) {
        tree[node] = val;
        return;
    }
    int mid = (l + r) / 2;
    if (i <= mid) update(2*node, l, mid, i, val);
    else          update(2*node+1, mid+1, r, i, val);
    tree[node] = tree[2*node] + tree[2*node+1];
}

Compare this with the Fenwick update: there you jump i += lowbit(i) through the cells that cover i, here you walk down the path of nodes that cover i. Same idea, different layout.

1.5 Range Query

To answer [ql, qr] we start at the root and for every node [l, r] there are only three cases:

  • No overlap (r < ql or l > qr): this node contributes nothing, return the identity (0 for sum).
  • Full overlap (ql ≤ l and r ≤ qr): the whole node is inside the query, return tree[node] directly without going deeper.
  • Partial overlap: ask both children and combine.
int query(int node, int l, int r, int ql, int qr) {
    if (r < ql || l > qr) return 0;              // no overlap
    if (ql <= l && r <= qr) return tree[node];   // full overlap
    int mid = (l + r) / 2;                         // partial overlap
    return query(2*node, l, mid, ql, qr)
         + query(2*node+1, mid+1, r, ql, qr);
}

For sum(2, 7) on the tree above: the root [0, 7] partially overlaps, so go to both children. [0, 3] partially overlaps, its child [0, 1] has no overlap (returns 0) and [2, 3] fully overlaps (returns 5). [4, 7] fully overlaps (returns 22). Answer = 5 + 22 = 27.

Why is this O(log N)? At any depth, at most two nodes are partial overlaps (the ones containing the left and right edges of the query), and every node in between is a full overlap that stops immediately. So we touch at most about 4 nodes per level, and there are log N levels.

operation            complexity
build                O(N)
update(i, val)       O(log N)
query(l, r)          O(log N)
space                O(4N)

1.6 Standard Implementation

Use this template for segment tree questions. Everything specific to the problem lives in combine and the identity value, so changing the operation means changing two lines.

struct segtree {
public:
    int n;
    vector<int> tree;
    const int IDENTITY = 0;              // 0 for sum, INT_MAX for min, INT_MIN for max

    int combine(int a, int b) {
        return a + b;                    // a + b, min(a, b), max(a, b), gcd(a, b) ...
    }

    segtree(vector<int>& arr) {
        n = arr.size();
        tree.assign(4*n, IDENTITY);
        build(arr, 1, 0, n-1);
    }

    void build(vector<int>& arr, int node, int l, int r) {
        if (l == r) { tree[node] = arr[l]; return; }
        int mid = (l + r) / 2;
        build(arr, 2*node, l, mid);
        build(arr, 2*node+1, mid+1, r);
        tree[node] = combine(tree[2*node], tree[2*node+1]);
    }

    void update(int node, int l, int r, int i, int val) {
        if (l == r) { tree[node] = val; return; }
        int mid = (l + r) / 2;
        if (i <= mid) update(2*node, l, mid, i, val);
        else          update(2*node+1, mid+1, r, i, val);
        tree[node] = combine(tree[2*node], tree[2*node+1]);
    }

    int query(int node, int l, int r, int ql, int qr) {
        if (r < ql || l > qr) return IDENTITY;
        if (ql <= l && r <= qr) return tree[node];
        int mid = (l + r) / 2;
        return combine(query(2*node, l, mid, ql, qr),
                       query(2*node+1, mid+1, r, ql, qr));
    }

    // wrappers so the call site stays clean
    void update(int i, int val) { update(1, 0, n-1, i, val); }
    int query(int l, int r)     { return query(1, 0, n-1, l, r); }
};

Note the segment tree here is 0 indexed while the Fenwick tree was 1 indexed. Both are fine, just be consistent inside each one.

1.7 Choosing the Operation

The only rule is that combine must be associative, i.e. combine(combine(a, b), c) = combine(a, combine(b, c)), because the tree splits a range wherever mid falls and we need the answer not to depend on how it was split. The identity must satisfy combine(x, IDENTITY) = x so that "no overlap" nodes don't change the answer.

operation   combine        identity
sum         a + b          0
min         min(a, b)      INT_MAX
max         max(a, b)      INT_MIN
gcd         gcd(a, b)      0
xor         a ^ b          0

Nodes can also store more than one number. For example storing (max, count of max) lets you answer "how many times does the maximum appear in [l, r]", as long as you can write a combine for two such pairs.

1.8 Range Updates with Lazy Propagation

Now suppose the update is also a range: add val to every element in [l, r]. Doing a point update for each element is O(N log N) per update which is too slow.

The idea of lazy propagation is to be lazy: when an update fully covers a node, update that node's value and leave a note (lazy[node]) saying "my children still owe this update", without going further down. The note is only pushed to the children later, when some query or update actually needs to go inside that node.

vector<long long> tree, lazy;            // both size 4N, range add + range sum

void push(int node, int l, int r) {
    if (lazy[node] == 0) return;
    int mid = (l + r) / 2;
    for (int c : {2*node, 2*node+1}) {
        int len = (c == 2*node) ? (mid - l + 1) : (r - mid);
        tree[c] += lazy[node] * len;
        lazy[c] += lazy[node];
    }
    lazy[node] = 0;
}

void range_add(int node, int l, int r, int ql, int qr, long long val) {
    if (r < ql || l > qr) return;
    if (ql <= l && r <= qr) {
        tree[node] += val * (r - l + 1);   // every element in this node got +val
        lazy[node] += val;                 // children still owe +val
        return;
    }
    push(node, l, r);
    int mid = (l + r) / 2;
    range_add(2*node, l, mid, ql, qr, val);
    range_add(2*node+1, mid+1, r, ql, qr, val);
    tree[node] = tree[2*node] + tree[2*node+1];
}

long long query(int node, int l, int r, int ql, int qr) {
    if (r < ql || l > qr) return 0;
    if (ql <= l && r <= qr) return tree[node];
    push(node, l, r);
    int mid = (l + r) / 2;
    return query(2*node, l, mid, ql, qr) + query(2*node+1, mid+1, r, ql, qr);
}

Range updates touch the same O(log N) nodes as a range query, so both range update and range query stay O(log N). The two things to get right are the length multiplier (adding val to a node of sum covering k elements adds val × k) and calling push before going into the children.

1.9 Segment Tree vs Fenwick Tree

                      fenwick tree          segment tree
point update          O(log N)              O(log N)
range query           O(log N)              O(log N)
operations            invertible (sum, xor) any associative (min, max, gcd ...)
range update          possible with tricks  lazy propagation
memory                N + 1                 4N
code                  ~15 lines             ~40 lines

Rule of thumb: if it's sums (or counts, like the inversion counting with compression in the Fenwick notes), use a Fenwick tree because it is shorter and faster. If it's min, max, gcd, anything that can't be undone, or range updates, use a segment tree. And for path queries on trees the two combine with LCA: flatten the tree with an Euler tour and put a BIT or segment tree on top.
