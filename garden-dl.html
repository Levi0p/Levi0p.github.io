Weight Initialization

Xavier / He Initialisation : Essentially when we set the weights for the neural network, firstly we want randomness so that there isn't symmetry in neurons but, if the weights are too large the gradients can explode and if weights are too small gradients shrink, we want the variance of gradients to remain stable, this init is performed at the very start, for Xavier we want the variance = 2/(nin+nout), so the weights are from the distribution N(0,sqrt(variance)) and for He/Kaiming init we have variance = 2/nin and weights are created from the distribution N(0,sqrt(variance))

We just control the starting weights with this

Gradient Clipping

The problem is that sometimes gradients can grow too large which will destroy everything, this is called exploding gradients, so we need a way to scale them down so they don't grow too large, for this we first calculate the norm of the vector, for V = [3,4], the norm = sqrt(3^2 + 4^2) = 5, and we set max_norm, if max_norm = 2 here, so 5 > 2 → we scale the vector down by 2/5 = 0.4 → V' = [1.2,1.6], gradient clipping is done after loss.backward() and before optimizer.step(), this is what we use :

torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)

Normalization Layers

Batch Normalisation → This is done to normalise the activations produced which leads to more stable optimization, say the layer outputs [x1,x2,x3] we first calculate the mean and then the variance and then we do X' = (X-mean)/sqrt(variance + epsilon), also we don't want to permanently enforce this pattern so we also add two learnable parameters : gamma and beta so, X'' = gamma * X' + beta, this allows it to scale and shift, also during training we can calculate the mean and variance using the batch i.e batch statistics but during inference we just have one example so we can't, so we also maintain running mean and running variance which we use during inference

Layer Normalisation → The whole process is just like BatchNorm, the only difference is how it is applied, if you consider a matrix of batch * no of features, in this matrix BatchNorm would be applied column wise but, for LayerNorm we do it row wise which makes it batch independent and can even work with batch_size = 1 and we have no need for running mean or running variance in LayerNorm, usually LayerNorm is used for transformers and BatchNorm for CNNs

Regularization: Dropout, Weight Decay, Label Smoothing

Dropout → The whole thinking behind dropout is to reduce the importance of individual neurons and to reduce overfitting, what happens is say a layer produced activations [2,6,4,8] and say p = 0.2 which means that 20% activations are dropped as in smth like [2,6,0,8], the neurons and weights are not removed only the activations are dropped, so say neuron A was important for a particular query, now the nn will have to rely on perhaps neurons B,C,D for the same task which reduces the importance of neuron A for that task which is good since it is all distributed now, also after dropping the rest of the activations are scaled by 1/(1-p), also during inference dropout is disabled

Weight Decay → It is used to penalise larger weights, this reduces overfitting, L = Ldata + lambda/2 * Σwi^2, and W' = W - n * dL = W - n * lambda * W so, W' = W(1 - n * lambda), this is L2 regularization and pushes the weights towards zero, AdamW uses decoupled weight decay

Label Smoothing → To decrease overconfidence in model, usually classification models, where instead of one-hot targets [0,1,0] we have smth like [0.05,0.9,0.05], this encourages better generalization

Transformer

First say we get an input sentence "The cat sat", it first gets tokenized then we use an embedding matrix and it looks smth like : X = [xthe xcat xsat], we also add the positional encodings in this, now we generate the Key, Query and Value matrices, the key is what do i contain?, the query is what am i looking for? and the value is what info do i give?, we get these by Q = XWq, K = XWk, V = XWv, this gives us for all the embeddings, now we need to calculate the self-attention and we do that by Attention = softmax(QKt/sqrt(dk)) * V, now this is one attention block, we can have multiple and this is now multi-head attention, from one head it will be Z1, from another head Z2, we concatenate this and then do matrix multiplication with wo to get Z which is what we will later pass to the ffn so now, a transformer block looks like :

Input → Multi-head Attention → Residual(X+A) + LayerNorm → Feedforward Neural Network(just a linear layer + ReLu + linear layer) → Residual + LayerNorm → Output

The full encoder-decoder flow :

Input sentence → Tokenize + Embeddings → Encoder → Self-Attention → Residual + LayerNorm → FFN → Residual + LayerNorm → Encoder Output → Decoder → Masked Self-Attention(a token can only look at itself and prev words) → Residual + LayerNorm → Cross-Attention ← Encoder Output (K,V) → Residual + LayerNorm → FFN → Residual + LayerNorm → Linear + Softmax → Output

RNNs, LSTMs and GRUs

RNN → It is a NN designed to process sequential data, it essentially keeps track of hidden states as well while processing and these hidden states represent the previous information, we use this equation : ht = f(Wxh*xt + Whh*ht-1 + bh) and yt = f(Why*ht + by), where ht is current memory and ht-1 is prev memory and xt is current input and the W's are just hidden weights and bh are the biases, for translations, in which the length of the input is diff than the output, that is a sequence to sequence model, there is a problem of exploding and vanishing gradients in RNNs, coz if the length goes on too long numbers can vanish or explode, we usually use gradient clipping and that somewhat solves the exploding gradients problem but for vanishing gradients we have to use LSTMs or GRU, also RNNs do smth called backpropagation through time

LSTMs → Long short term memory, this resolves the problem of shrinking gradients in RNNs which is caused due to multiple multiplications of numbers <1 through backpropagation through time, alongside a ht hidden state they also use another state called cell state ct, ct has the long term memory, now there are three gates which are forget gate, input gate, output gate, ft = sigma(wf*[ht-1,xt] + bf) and it = sigma(wi*[ht-1,xt] + bi), and proposed candidate memory c~t = tanh(Wc*[ht-1,xt] + bc), and ct = ft . ct-1 + it . c~t, note that you will see ft being element wise multiplied with ct-1, this is to see how much of the prev cell state to keep and it is element wise multiplied with the candidate cell state to see how much should enter the memory, and the ot = sigma(wo*[ht-1,xt] + bo) and finally ht = ot . tanh(ct), all this helps in reducing vanishing gradients coz if ft is close to 1, gradients can pass through more effectively

GRU → Gated Recurrent Unit, they only have two gates, an update gate and a reset gate, GRU generally has less parameters than LSTMs and it doesn't have a ct it just has a ht

Teacher forcing → During training of an autoregressive decoder, instead of feeding the model's previous prediction as the next input, we feed the ground-truth previous token

Training a New Tokenizer

If the existing tokenizer is not suitable for your language or domain, you can train a new tokenizer on a corpus of your target data, most Transformer models use subword tokenization and tokenizer training is a deterministic statistical process that finds useful/frequent subwords, unlike model training which uses stochastic gradient descent. First collect a representative corpus, then process it in batches using an iterator/generator so the whole dataset does not have to be loaded into memory at once, generators load data lazily when needed, and a generator object can only be used once, so you can define a function that creates a new generator

Fast Tokenizers

Fast tokenizers are backed by the Hugging Face Tokenizers library written in Rust, while slow tokenizers are written in Python, faster speed is coz of parallelism. Fast tokenizers keep track of the original character span (offset mapping) that each token came from, which lets you map tokens ↔ words ↔ characters. You can check whether a tokenizer is fast with tokenizer.is_fast or encoding.is_fast, get the tokens with encoding.tokens(), get the original word corresponding to each token with encoding.word_ids(), and get sentence IDs with sentence_ids(). Special tokens such as [CLS] and [SEP] have None as their word ID. You can also use word_to_chars(), token_to_chars(), char_to_word(), and char_to_token() to move between words, tokens, and character positions. The definition of a word depends on the tokenizer/pre-tokenization, so different tokenizers may split things differently.

For token classification/NER, the input is tokenized and passed through a token-classification model, which gives a set of logits for every token; for example, with 19 tokens and 9 labels, the output shape is 1 × 19 × 9. Apply softmax to get probabilities and argmax to choose the predicted label; argmax can be taken directly on the logits because softmax does not change their ordering.

The model's id2label maps label IDs to labels such as O, B-PER, I-PER, B-ORG, I-ORG, B-LOC, and I-LOC; O means outside any entity, B-XXX means the beginning of entity type XXX, and I-XXX means inside that entity. The chapter also explains IOB1 vs IOB2, where IOB1 can use I-XXX for the first token of an entity in some cases.

Offset mapping is what lets you recover the exact character span of each predicted entity: each token gets a (start,end) character span, and special tokens use (0,0), so you can directly slice the original text to recover the entity. This is especially useful for grouping subword tokens into complete entities without tokenizer-specific rules; for example, Hu, ##gging, and Face can be combined simply by taking the original text span from the first token's start to the last token's end.

When grouping NER predictions, consecutive tokens of the same entity type are combined, and the score can be calculated in different ways: "simple" uses the mean token score, "first" uses the first token's score, "max" uses the maximum token score, and "average" averages the scores of the words in the entity.

Fast Tokenizers in QA

The question-answering pipeline uses a tokenizer and a QA model to find an answer span inside a context, and fast tokenizers are especially useful because they provide offset mappings that let us convert token positions back to character positions in the original text. For QA, the input is tokenized as [CLS] question [SEP] context [SEP], and the model outputs two sets of logits, one for the token where the answer starts (start_logits) and one for where it ends (end_logits). Before applying softmax, we mask tokens that are not part of the context, while keeping [CLS] because some models can use it to indicate that the answer is not in the context; then softmax converts the logits into start/end probabilities.

We cannot simply take the independent argmax of the start and end probabilities because we could get start > end, so we consider possible start/end pairs and keep only valid spans where start ≤ end, then choose the highest-scoring span. The span score is calculated from the start and end probabilities, and the resulting token positions are converted to character positions using the tokenizer's offset mapping, allowing us to extract the actual answer from the original context.

For long contexts, the input may exceed the model's maximum sequence length, so we truncate only the context using truncation="only_second". But this can remove the answer, so instead we split the context into overlapping chunks using return_overflowing_tokens=True, max_length, and a stride; the overlap ensures an answer near a chunk boundary is less likely to be lost. overflow_to_sample_mapping tells us which original input each chunk came from. Each chunk is processed separately, giving separate start/end logits, and we find the best answer span across all chunks, then use the offsets to recover the corresponding characters from the original long context.

Normalization and Pre-tokenization

Before subword tokenization, the tokenizer first does normalization and pre-tokenization. Normalization cleans the text, such as removing unnecessary whitespace, lowercasing, removing accents, and possibly applying Unicode normalization; for example, bert-base-uncased turns "Héllò hôw are ü?" into "hello how are u?". Pre-tokenization then splits the text into smaller units such as words, usually using whitespace and/or punctuation, and these units become the boundaries from which the subword tokenizer learns.

Different tokenizers use different pre-tokenization rules: BERT splits on whitespace and punctuation and ignores repeated spaces, GPT-2 also splits on whitespace and punctuation but keeps spaces using the Ġ symbol, while T5/SentencePiece mainly splits on whitespace and uses ▁ to represent spaces.

SentencePiece

SentencePiece treats text as a sequence of Unicode characters and represents spaces with the special character ▁. When used with Unigram, it does not require pre-tokenization, which is useful for languages such as Chinese or Japanese where spaces may not separate words. SentencePiece also supports reversible tokenization: tokens can be decoded by concatenating them and replacing ▁ with spaces, whereas BERT's normalization can make its tokenization non-reversible because repeated spaces are removed.

BPE vs WordPiece vs Unigram

BPE starts with a small vocabulary and repeatedly merges the most common token pair; it learns merge rules + a vocabulary, and during encoding it applies those learned merges. WordPiece also starts with a small vocabulary and merges tokens, but chooses pairs using a score based on pair frequency that favors pairs whose individual tokens are less frequent; it learns only the vocabulary, and during encoding it finds the longest vocabulary subword from the beginning of the word, then continues. Unigram starts with a large vocabulary and repeatedly removes tokens that reduce the loss the least; it learns a vocabulary plus a score for each token, and during encoding chooses the most likely tokenization using those scores.

Byte-Pair Encoding (BPE)

Byte-Pair Encoding is a subword tokenization algorithm used by models such as GPT, GPT-2, RoBERTa, BART, and DeBERTa. During training, BPE first takes the unique words from the normalized/pre-tokenized corpus and builds a base vocabulary from the characters appearing in those words; then it repeatedly finds the most frequent pair of consecutive tokens and merges them into a new token, adding that token to the vocabulary, and continues until the desired vocabulary size is reached. So BPE learns merge rules + a vocabulary. For example, starting from h u g, p u g, etc., if (u,g) is the most frequent pair, it learns (u,g) → ug, then it keeps finding the most frequent pair and merging it, eventually creating longer subwords such as hug.

Byte-level BPE → GPT-2 and RoBERTa use bytes instead of Unicode characters for the initial vocabulary, giving a base vocabulary of 256 possible bytes, so essentially every character can be represented and you avoid unknown-character problems such as [UNK].

BPE tokenization of new text works by normalization → pre-tokenization → splitting each word into characters/initial tokens → applying the learned merge rules in order. For example, if the learned rules are (u,g)→ug, (u,n)→un, and (h,ug)→hug, then "bug" becomes ["b","ug"]; the learned rules are then applied to construct the final subwords.

The main thing to understand is: BPE starts small and builds bigger tokens by repeatedly merging the most frequent adjacent pair. The final vocabulary consists of the initial vocabulary plus all the tokens created by those merges.

WordPiece

WordPiece is the subword tokenization algorithm developed by Google for BERT and later used by models such as DistilBERT and MobileBERT. It is similar to BPE during training, but the way it tokenizes new words is different. WordPiece starts with a small vocabulary containing special tokens and the initial alphabet; characters inside a word get the ## prefix, so word starts as w ##o ##r ##d. During training, instead of choosing the most frequent pair like BPE, WordPiece calculates a score for each adjacent pair: score = frequency of pair / (frequency of first element × frequency of second element), so it favors pairs whose individual parts are relatively less frequent. It repeatedly merges the pair with the highest score until the desired vocabulary size is reached.

WordPiece only saves the final vocabulary, not the merge rules. When tokenizing a new word, it finds the longest subword starting from the beginning that exists in the vocabulary, takes it, then repeats for the remaining part of the word. For example, hugs can become ["hug", "##s"]. If at any point no valid subword can be found, the entire word becomes [UNK], unlike BPE, which can mark only unknown individual characters/tokens as unknown.

So the main difference to remember is: BPE = repeatedly merge the most frequent pair and store merge rules; WordPiece = repeatedly merge the highest-scoring pair and store the final vocabulary, then tokenize by greedily taking the longest matching subword.

Unigram

Unigram is used together with SentencePiece and is used by models such as T5, ALBERT, mBART, BigBird, and XLNet. Unlike BPE and WordPiece, which start with a small vocabulary and add/merge tokens, Unigram starts with a large vocabulary and repeatedly removes tokens until the desired vocabulary size is reached. The initial vocabulary can be built from common substrings, and the basic characters are always kept so every word can still be tokenized. At each step, Unigram computes the loss of the corpus and checks how much the loss would increase if each token were removed; tokens whose removal increases the loss the least are considered less useful and are removed, usually removing a percentage of them at each step.

In SentencePiece, the input is treated as a raw character stream including spaces, with spaces represented by ▁, which means it can work for languages that do not use spaces between words. In the Unigram model, each token has a probability based on its frequency in the corpus. To tokenize a word, Unigram considers possible segmentations and chooses the one with the highest probability, where the probability of a segmentation is the product of the probabilities of its individual tokens. Because multiplying many small probabilities is inconvenient, the implementation can work with log probabilities instead. The Viterbi algorithm is used to efficiently find the highest-probability segmentation instead of checking every possible segmentation manually.

So the main difference is: BPE → start small and merge the most frequent pairs; WordPiece → start small and merge the highest-scoring pairs; Unigram → start large and remove the least useful tokens based on their effect on corpus loss.
