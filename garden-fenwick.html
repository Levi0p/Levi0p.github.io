1.1 Fenwick Tree: Motivation & Problem Setup

Suppose you are given an array of N integers and you must handle two types of queries repeatedly:

  • Point Update: add a value val to arr[i].
  • Range Sum Query: compute arr[l] + arr[l+1] + … + arr[r].

A brute force solution takes O(1) update and O(N) query, or O(N) update (prefix array) and O(1) query. Neither is efficient enough when both operations are frequent. A Fenwick Tree (Binary Indexed Tree) solves both in O(log N), using only O(N) extra space, which is less memory than a Segment Tree and simpler to code.

1.2 The Lowbit / LSB Trick

The key to understanding a Fenwick Tree is i & (−i), which extracts the lowest set bit of i, telling us how many elements are covered at that index.

idx        1  2  3  4  5  6  7  8
arr[idx]   3  1  4  1  5  9  2  6

The Bit vector stores partial sums in a way that each index i is responsible for a range [l, r] determined by its lowest set bit, and bit[i] = arr[l] + … + arr[r]. To find l and r: r = i, and for l take i in binary, unset the lowest bit and add 1. E.g. i = 6 is 0110, unset the lowest bit → 0100, add 1 → 0101 (5). So for i = 6, l = 5 and r = 6.

i        1      2      3      4      5      6      7      8
[l,r]  [1,1]  [1,2]  [3,3]  [1,4]  [5,5]  [5,6]  [7,7]  [1,8]

So for i = 4, bit[4] = arr[1] + arr[2] + arr[3] + arr[4] = 3 + 1 + 4 + 1 = 9.

idx        1  2  3  4  5   6  7   8
bit[idx]   3  4  4  9  5  14  2  31

For any index i, the trick is 2's complement negation. To compute −i, you flip all bits and add 1. When you AND that with i, all higher bits cancel and only the lowest set bit survives. That single bit tells you how many elements bit[i] is responsible for.

lowbit(i) = i & (−i), which isolates the lowest set bit

The range is always [i − lowbit(i) + 1, i], i.e. it ends at i and stretches left by lowbit(i) positions.

operation          complexity
update(i, delta)   O(log N)
query(l, r)        O(log N)
space              O(N)

To find the prefix sum of arr[1..6], we start at i = 6, whose binary representation is 0110. We can think of 0110 as 0100 + 0010, i.e. 4 + 2. This decomposition is exactly what the query loop does, at each step it strips the lowest set bit and jumps left:

  • i = 6 → lowbit(6) = 2, so bit[6] covers arr[5..6]. Add bit[6] = 14. Move to i = 6 − 2 = 4.
  • i = 4 → lowbit(4) = 4, so bit[4] covers arr[1..4]. Add bit[4] = 9. Move to i = 4 − 4 = 0. Stop.

So prefix_sum(6) = 14 + 9 = 23. The key insight is that the binary bits of 6 (0110) directly tell you which bit cells to visit, each set bit corresponds to one bit cell, and together they tile arr[1..6] with no gaps and no overlaps.

Update goes the other way: adding lowbit(i) to i jumps to the next cell whose range also contains i, so a point update touches every cell that covers it, again O(log N) of them.

1.3 Standard Implementation (1 indexed)

Always use 1 indexed arrays with a BIT. Index 0 is never touched (lowbit(0) = 0, so the loops would never move). Use this template for Fenwick tree questions:

struct fenwick {
public:
    int n;
    vector<int> bit;

    fenwick(int size) {
        n = size;
        bit.assign(n + 1, 0);
    }

    void update(int i, int val) {
        while (i <= n) {
            bit[i] += val;
            i += (i & (-i));
        }
    }

    int query(int i) {          // prefix sum arr[1..i]
        int ans = 0;
        while (i) {
            ans += bit[i];
            i -= (i & (-i));
        }
        return ans;
    }
};

A range sum is then just two prefix sums: sum(l, r) = query(r) − query(l − 1).

1.4 How to Use the Template

The way you initialise and use the Fenwick tree depends on the size of the values you are dealing with.

Case 1: values ≤ 10⁵. The values are small enough to be used directly as indices, so no compression is needed. Simply declare fenwick ft(n); and use ft.update(i, val) and ft.query(i) directly with the values.

Case 2: values ≤ 10⁹. The values are too large to use as indices, so we first compress them down to a small range:

vector<int> val = arr;
sort(val.begin(), val.end());
val.erase(unique(val.begin(), val.end()), val.end());

fenwick ft(val.size());
int ans = 0;
for (int i = 0; i < n; i++) {
    // compressed index of arr[i] (1 indexed)
    int idx = lower_bound(val.begin(), val.end(), arr[i]) - val.begin() + 1;

    // ft.query(idx) = count of elements inserted so far with value <= arr[i]
    ans += ft.query(idx);
    ft.update(idx, 1);
}
cout << ans << endl;

The key idea is that lower_bound maps each original value to its rank in the sorted unique array, giving it a compressed index between 1 and val.size(). The Fenwick tree then operates on these small indices instead of the raw values, keeping everything efficient.

2.1 Binary Lifting: Trees

A tree is a connected acyclic graph with N nodes and N − 1 edges. We usually root it at node 1. Key terms:

  • Parent: the node immediately above a given node on the path to the root.
  • Depth: depth[root] = 0; depth[v] = depth[parent[v]] + 1.
  • Ancestor: node u is an ancestor of v if u lies on the path from v to the root.

2.2 Motivation: K-th Ancestor

Given a rooted tree, answer Q queries of the form "what is the k-th ancestor of node v?"

Naive: walk up k steps, O(N) per query, O(NQ) total. For N, Q = 10⁵ this is too slow.

Binary Lifting precomputes up[v][j] = the 2j-th ancestor of v, for j = 0, 1, …, LOG − 1. Then any k-th ancestor can be found in O(log N) by decomposing k in binary, the same idea as the Fenwick query above.

Very important: binary lifting doesn't work if updates to the tree are involved, since the whole table would have to be rebuilt.

2.3 Precomputation

const int MAXN = 1e5 + 5;
const int LOG  = 20;

int up[MAXN][LOG];     // up[v][j] = 2^j-th ancestor of v
int depth[MAXN];
vector<int> g[MAXN];

void dfs(int v, int par) {
    up[v][0] = par;
    for (int j = 1; j < LOG; j++)
        up[v][j] = up[ up[v][j-1] ][j-1];

    for (int child : g[v]) {
        if (child != par) {
            depth[child] = depth[v] + 1;
            dfs(child, v);
        }
    }
}

// depth[root] = 0; up[root][j] = root for all j
// dfs(root, root);

The recurrence is up[v][j] = up[up[v][j−1]][j−1], i.e. the 2j-th ancestor is the 2j−1-th ancestor of the 2j−1-th ancestor. It works inside the DFS because a node's ancestors are always visited before it, so their rows are already filled in.

2.4 K-th Ancestor Query

int kth_ancestor(int v, int k) {
    for (int j = 0; j < LOG; j++)
        if ((k >> j) & 1)       // j-th bit of k is set
            v = up[v][j];
    return v;
}

For example 11 = 1011₂, so bits 0, 1 and 3 are set:

  • Step 1: move 2⁰ = 1 step: v = up[v][0]
  • Step 2: move 2¹ = 2 steps: v = up[v][1]
  • Step 3: move 2³ = 8 steps: v = up[v][3]

Total: 1 + 2 + 8 = 11 steps.

2.5 Augmented Binary Lifting

You can store extra information along the path. Common extensions:

  • Max edge weight: up_max[v][j] = max edge weight on the path from v to its 2j-th ancestor.
  • Min edge weight: similarly up_min[v][j].
  • Sum of values: up_sum[v][j] = sum of node values from v up to (but not including) its 2j-th ancestor.
int up_max[MAXN][LOG];

// during DFS:
up_max[v][0] = weight of edge (v, parent[v]);
for (int j = 1; j < LOG; j++)
    up_max[v][j] = max(up_max[v][j-1], up_max[ up[v][j-1] ][j-1]);

This works for any operation where two halves of a jump can be combined, which is the same condition a segment tree needs.

3.1 What is LCA?

Given a rooted tree, the Lowest Common Ancestor (LCA) of two nodes u and v is the deepest node that is an ancestor of both u and v.

Think of a family tree. lca(u, v) is the most recent common ancestor, the first node where the paths from u to root and v to root meet.

dist(u, v) = depth[u] + depth[v] − 2 × depth[lca(u, v)]

This single formula converts path distance queries into LCA queries.

3.2 LCA via Binary Lifting

This is the most important application of binary lifting in competitive programming.

int lca(int u, int v) {
    // 1. bring u and v to the same depth
    if (depth[u] < depth[v]) swap(u, v);
    int diff = depth[u] - depth[v];
    for (int j = 0; j < LOG; j++)
        if ((diff >> j) & 1)
            u = up[u][j];

    // 2. if they are the same node, we're done
    if (u == v) return u;

    // 3. lift both until their parents match
    for (int j = LOG - 1; j >= 0; j--)
        if (up[u][j] != up[v][j]) {
            u = up[u][j];
            v = up[v][j];
        }

    return up[u][0];
}

Step 3 is subtle: we go from LOG − 1 down to 0, always jumping when it is safe (up[u][j] ≠ up[v][j]). This guarantees u and v end up as the children of the LCA, not above it. If we jumped whenever the ancestors were equal we could overshoot to some common ancestor higher up, so we only ever jump to nodes that are still different and the answer is one step above where we stop.

operation                complexity
precomputation           O(N log N) time, O(N log N) space
lca(u, v)                O(log N)
dist(u, v)               O(log N)
path max/min edge        O(log N) with augmented lifting

3.3 LCA: Key Problem Patterns

Pattern 1: path queries on trees. Any query of the form "compute something over the path from u to v" can be split at the LCA:

  • path(u, v) = path(u, lca) + path(v, lca)
  • With a BIT on DFS in-time (Euler tour), you can compute prefix sums from the root, then sum(u, v) = prefix(u) + prefix(v) − prefix(lca) − prefix(parent(lca)).

Pattern 2: tree distance queries.

int dist(int u, int v) {
    return depth[u] + depth[v] - 2 * depth[lca(u, v)];
}

Pattern 3: counting nodes on a path. Nodes on path(u, v) = depth[u] + depth[v] − 2 × depth[lca] + 1.
